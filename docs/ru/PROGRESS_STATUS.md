# Статус прогресса ревью

Ревью, запущенные webhook'ом и вручную (`POST /api/v1/reviews`), публикуют прогресс на head-коммите PR, чтобы автор видел, поставил ли бот PR в очередь, работает, пропустил его или сломался, без лишнего комментария. Включено по умолчанию; существующие файлы `config.yaml` менять не нужно.

```yaml
progress_status:
  enabled: true
  mode: auto          # auto | check_run | commit_status | off (auto = check_run for a GitHub App, commit_status for a PAT)
  reaction: false     # add an eyes reaction while a worker reviews the PR
  timeout_seconds: 5  # per GitHub call
```

Ключи и диапазоны: [CONFIGURATION.md](CONFIGURATION.md#progress_status). Любое поле можно переопределить для owner'а в `owners.<id>.progress_status`, например `mode: off` для owner'а, чьим кредам не хватает права.

<!-- section: github-app-check-run-autoreview -->
## GitHub App: check run `autoreview`

- `queued`, когда запрос принят и job поставлена в очередь, `in_progress`, когда её берёт worker, затем `completed`.
- Итоги: `success` (нет замечаний P0–P2), `neutral` (есть замечания P0–P2), `skipped` (причина в summary: draft, fork, репозиторий не разрешён, автор без права write, size guard, owner отключён или сменился), `cancelled` (вытеснен более новым push или head сменился во время ревью), `failure` (только ошибки бота и таймауты).
- Замечания никогда не дают `failure`, поэтому проверка не может блокировать merge.
- Нужно право App **Checks: Read and write**.

<!-- section: pat-commit-status-autoreview -->
## PAT: commit status `autoreview`

- `pending` в очереди и во время работы, затем `success` (ревью опубликовано или пропущено), `failure` (ошибка бота или таймаут) или `error` (отменено).
- Однострочное описание и `target_url`, указывающий на комментарий ревью.
- Fine-grained PAT нужно **Commit statuses: Read and write**; classic PAT нужен `repo:status` (входит в `repo`).

<!-- section: review-phases -->
## Фазы ревью

Пока прогон открыт, summary check run и описание commit status показывают текущую фазу и время её начала в UTC (тот же формат, что в комментарии ревью):

| Фаза | Текст | Check run | Commit status |
| --- | --- | --- | --- |
| queued | `[2026-10-24 21:20:01 UTC] (1/5) Queued, waiting for a worker…` | `queued` | `pending` |
| fetching | `[2026-10-24 21:20:05 UTC] (2/5) Fetching pull request and diff…` | `in_progress` | `pending` |
| context | `[2026-10-24 21:20:07 UTC] (3/5) Reading repository context…` (задача Jira, clone) | `in_progress` | `pending` |
| analyzing | `[2026-10-24 21:20:12 UTC] (4/5) Running model analysis…` | `in_progress` | `pending` |
| publishing | `[2026-10-24 21:23:24 UTC] (5/5) Publishing results…` | `in_progress` | `pending` |

- Статус пишется один раз при смене фазы, никогда по таймеру: не больше пяти записей до финальной, поэтому лимиты GitHub не проблема. Повторная фаза ничего не пишет.
- У каждой фазы фиксированный номер шага после времени, `(n/5)`. Если путь пропускает фазу, номера не меняются: слишком большой PR идёт с `(3/5)` сразу на `(5/5)`.
- Строка фазы всегда укладывается в лимит commit status 140 символов; обрезается только текст фазы, время и номер шага сохраняются.
- Запись фаз — best effort, как любая запись статуса: ошибка логируется, ревью продолжается. Фаза сохраняется в отдельной короткой транзакции базы (строка прогона блокируется, ожидание не больше 2 с), отдельно от транзакции самого ревью, поэтому неудачная запись фазы не может повлиять на ревью.
- Тексты статуса только на английском; `language.*` влияет на комментарий ревью, а не на статус.
- В финальном описании commit status времени ревью нет, поэтому оно всегда укладывается в 140 символов вместе с замечаниями и задачей Jira. Summary check run и комментарий ревью сохраняют полное время и длительность.

**Как заметить зависшее ревью:** время фазы перестаёт меняться. Анализ моделью обычно самый долгий (до `codex.timeout_seconds` на попытку, две попытки); фаза старше этого или любая фаза старше `WORKER_JOB_TIMEOUT` означает, что прогон застрял. Таймаут job и job очистки ниже закрывают такие статусы как failed.

<!-- section: reliability -->
## Надёжность

- Каждый статус пишется собственными кредами owner'а прогона; `auto` выбирает режим для каждого owner'а по типу его кредов.
- Всё best effort: отсутствие права, ошибка GitHub или медленный вызов (ограничен `timeout_seconds`) логируются и игнорируются и никогда не проваливают и не задерживают ревью. Деплои без права продолжают работать, просто без статуса. Пропуски на уровне webhook (draft, fork, репозиторий не разрешён) публикуются во время запроса webhook и добавляют к ответу не больше `timeout_seconds`.
- Worker задаёт финальное состояние в блоке `finally`, в том числе при ошибках и таймауте job ARQ. Cron-job worker'а каждые 10 минут помечает статусы, всё ещё открытые после `WORKER_JOB_TIMEOUT` плюс 5 минут, как истёкшие, поэтому упавший worker не может оставить статус pending навсегда.
- Новый push создаёт новый check run на новом head и помечает всё ещё открытый прогон для предыдущего SHA как `cancelled`.
- Порядок записи: строка прогона коммитится до постановки job в очередь. Если постановка не удалась (например, Redis недоступен), прогон становится `failed` / `QUEUE_UNAVAILABLE`, и статус не создаётся. Статус queued пишется после успешной постановки, при заблокированной строке прогона и только пока прогон ещё pending, поэтому более новое состояние быстрого worker'а никогда не перезаписывается и создаётся только один check run.
- Если head PR сдвинулся между постановкой в очередь и взятием в работу, worker не ревьюит новый код под старым прогоном: он закрывает прогон как `HEAD_CHANGED` (статус `cancelled` на собственном SHA прогона) и никогда не публикует статус на другом коммите.
- Сериализация очереди, 60-секундная отсрочка для выполняющихся прогонов и условный захват `pending → running` описаны в [API.md](API.md#гарантии-конкурентности). Пропуски по причинам owner'а до захвата используют то же условие `pending`: если прогон уже держит другая job, ничего не пишется и её статус не трогается. Job, которую ARQ повторяет после падения worker'а, находит свой прогон в `running` и пропускается; следующий запрос для этого SHA заменяет его, а job очистки закрывает зависший статус.

<!-- section: same-commit-two-triggers -->
## Один коммит, два триггера

- Одновременно открыт не больше чем один статус на коммит.
- Ручной прогон с `force: true` (по умолчанию) заменяет открытый прогон на том же SHA, в том числе прогон webhook: статус старого прогона закрывается как `cancelled`, новый прогон получает свой.
- Webhook (или `force: false`) на SHA с открытым прогоном переиспользует этот прогон и его статус.
- Worker, чей статус уже закрыт более новым прогоном, больше в него не пишет.
- Открытый прогон, чья job потеряна, закрывается как `failure`, когда его заменяют.

<!-- section: manual-runs -->
## Ручные прогоны

Ручные прогоны публикуют статус так же, как прогоны webhook: те же креды и режим owner'а, порядок записи, пропуски, отмена и правила раскрытия. Прогон привязывается к текущему head PR; устаревший `head_sha` отклоняется с `409 stale_head_sha` до любой публикации ([API.md](API.md#ошибки)). `"report_status": false` запускает прогон без статуса; открытый статус заменяемого прогона всё равно закрывается. Ошибки запроса (неизвестный owner, репозиторий не разрешён, GitHub недоступен) — это ошибки HTTP, статуса они не создают.

Плановые прогоны дайджеста статуса не публикуют: они не ревьюят head PR.

<!-- section: owners-disabled-or-removed -->
## Owner отключён или удалён

- **Owner отключён** после webhook (`owner_disabled`): worker или job очистки для зависшего статуса закрывает статус как `skipped` собственными кредами этого owner'а. Реестр хранит креды отключённого owner'а только для этого; если их не удаётся загрузить, статус закрывается только в базе.
- **Owner удалён** из конфига (`owner_not_configured`): **его открытые статусы нельзя закрыть в GitHub.** Кредов для него нет, а бот никогда не использует креды другого owner'а или глобальные, поэтому check run остаётся `queued` / `in_progress` (или commit status `pending`). Job очистки закрывает его в базе и пишет предупреждение. Чтобы этого избежать, сначала отключите owner'а (`enabled: false`), дайте его прогонам в очереди завершиться, затем удалите блок; или закройте check run'ы вручную.

<!-- section: review-comment -->
## Комментарий ревью

Sticky-комментарий в PR начинается с вердикта, проверенного коммита и времени окончания анализа, всегда в UTC, с длительностью:

```text
**Reviewed:** commit `abc1234` at 2026-10-24 09:25:40 UTC (took 3m 12s)
```

С `language.details: ru` подписи на русском (`Проверено: коммит abc1234 в 2026-10-24 09:25:40 UTC (заняло 3 мин 12 с)`). Затем идут summary, карточки замечаний и, после повторного ревью, таблица **Previous finding transitions** с колонкой серьёзности:

| Status | Severity | Finding | Path |
| --- | --- | --- | --- |
| `still_open` | 🟠 P1 | Token is not validated | `app/auth.py:12` |
| `resolved` | P2 | Missing timeout | `app/client.py:40` |

Замечания, которые всё ещё открыты (`still_open`, `regressed`, `needs_human`), получают светофор перед серьёзностью: 🔴 P0, 🟠 P1, 🟡 P2, 🟢 P3. Исправленные (`resolved`, `obsolete`) показывают только серьёзность. По [политике для публичных репозиториев](PUBLIC_DISCLOSURE.md#замечания-безопасности-security_findings) отредактированная строка сохраняет серьёзность и светофор; заменяется только заголовок на общую подпись.

Карточки в разделе **Still open from previous review** используют тот же маркер перед статусом, например `#### [🟠 P1] [regressed] Token is not validated`; отредактированная карточка тоже его сохраняет (`#### [🟠 P1] Potential security issue.`).

<!-- section: what-a-status-discloses -->
## Что раскрывает статус

Summary содержат только состояние, причину пропуска или код ошибки, число замечаний и ссылку на комментарий; summary check run опубликованного ревью заканчивается временем ревью на английском, например `Reviewed commit abc1234 at 2026-10-24 09:25:40 UTC (took 3m 12s).` (в описании commit status его нет). Пока прогон открыт, они показывают только текущую фазу и время её начала. Текста модели, деталей замечаний и текста Jira в них никогда нет. Ключ задачи и соответствие задаче добавляются для приватных репозиториев; для публичных показывается только ключ и только при `public_repos.jira_disclosure` `key_only` или `full`.

<!-- section: has-sensitive-content -->
## `has_sensitive_content`

Каждый прогон записывает `comment_url` и `has_sensitive_content`: содержал бы опубликованный им комментарий ревью детали замечаний безопасности или текст Jira (невыполненные критерии приёмки или любой текст ревью, написанный с контекстом Jira в промпте) до применения политики для публичных репозиториев. `NULL` означает «неизвестно»: прогоны до миграции `008_review_run_progress` и прогоны, не опубликовавшие комментарий ревью. Флаг — заготовка для будущего админского представления; пока на него ничего не опирается.
