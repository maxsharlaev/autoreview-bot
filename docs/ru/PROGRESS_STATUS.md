# Статус прогресса ревью

Ревью, запущенные вебхуком или вручную (`POST /api/v1/reviews`), показывают прогресс на head-коммите PR: автор видит, что бот поставил PR в очередь, работает, пропустил его или сломался, без лишних комментариев. Английская версия — раздел «Review progress status» в [README](../../README.md).

```yaml
progress_status:
  enabled: true
  mode: auto          # auto | check_run | commit_status | off (auto = check_run для GitHub App, commit_status для PAT)
  reaction: false     # реакция eyes на PR, пока worker делает ревью
  timeout_seconds: 5  # на один вызов GitHub
```

По умолчанию включено, менять существующий `config.yaml` не нужно.

## GitHub App: check run `autoreview`

- `queued` — запрос принят и задача в очереди; `in_progress` — задачу взял worker; затем `completed`.
- Итог: `success` (нет замечаний P0–P2), `neutral` (есть замечания P0–P2), `skipped` (причина в summary: draft, fork, репозиторий не разрешён, у автора нет write, size guard, owner отключён или сменился), `cancelled` (новый push или смена head во время ревью), `failure` — только ошибки бота и таймауты.
- Замечания никогда не дают `failure`, поэтому check не блокирует merge.
- Нужно право App **Checks: Read and write**.

## PAT: commit status `autoreview`

- `pending` в очереди и во время ревью, затем `success` (ревью опубликовано или пропущено), `failure` (ошибка бота или таймаут) или `error` (отменено).
- Однострочное описание и `target_url` на комментарий ревью.
- Fine-grained PAT: **Commit statuses: Read and write**; классический PAT: `repo:status` (входит в `repo`).

## Надёжность

- Статус пишется учётными данными owner'а этого прогона; `auto` выбирает режим по типу учётных данных owner'а.
- Всё best effort: нет права, ошибка GitHub или медленный ответ (не дольше `timeout_seconds`) только логируются и не ломают и не задерживают ревью. Деплои без нового права продолжают работать, просто без статуса. Пропуски на уровне вебхука (draft, fork, репозиторий не разрешён) отправляются в самом запросе вебхука и добавляют к ответу не больше `timeout_seconds`.
- Финальное состояние ставится в `finally`, в том числе при ошибке и таймауте задачи arq.
- Cron worker'а раз в 10 минут помечает как истёкшие статусы, открытые дольше `WORKER_JOB_TIMEOUT` плюс 5 минут: упавший worker не оставит статус висеть.
- Новый push создаёт новый check run на новом head, а незавершённый run для предыдущего SHA помечается `cancelled`.
- Порядок записи: строка прогона коммитится до постановки задачи в очередь. Если поставить задачу не удалось (например, Redis недоступен), прогон помечается `failed` / `QUEUE_UNAVAILABLE`, и статус не создаётся. Статус queued пишется после успешной постановки, под блокировкой строки прогона и только пока прогон ещё в ожидании: быстрый worker не будет перезаписан, и check run создаётся один.
- Owner отключён после вебхука (`owner_disabled`): worker, а для зависшего статуса — cleanup, закрывает статус как `skipped` учётными данными этого же owner'а. Реестр хранит учётные данные отключённого owner'а только для этого; если их не удалось загрузить, статус закрывается только в базе.
- Owner удалён из конфига (`owner_not_configured`): **его открытые статусы на GitHub закрыть нельзя.** Учётных данных нет, а чужие или глобальные учётные данные бот для этого не использует, поэтому check run остаётся `queued` / `in_progress` (commit status — `pending`) на этом коммите. Cleanup закрывает его только в базе и пишет warning в лог. Чтобы этого избежать, сначала отключите owner'а (`enabled: false`) и дождитесь обработки его очереди, а потом удаляйте блок; либо закройте check run вручную.
- **Ручные прогоны** (`POST /api/v1/reviews`) публикуют статус так же, как вебхук: те же учётные данные owner'а и режим, порядок записи, пропуски, отмена и правила раскрытия. `"report_status": false` в запросе запускает прогон без статуса; открытый статус предыдущего прогона при этом всё равно закрывается. Ошибки запроса (неизвестный owner, репозиторий не разрешён, GitHub недоступен — `502`) возвращаются HTTP-ошибкой, статус не создаётся.
- Ручной эндпойнт всегда читает текущий PR из GitHub и привязывает прогон к его текущему head. Если в запросе передан `head_sha` и он не равен текущему head (полный SHA, без учёта регистра), ответ **409** `{"detail": {"code": "stale_head_sha", "head_sha": "<запрошенный>", "current_head_sha": "<текущий>"}}` — до любой отмены, записи в БД, постановки в очередь и статуса. `base_sha` из запроса игнорируется, берётся текущий base из GitHub.
- Постановка в очередь сериализуется по PR advisory-блокировкой Postgres (репозиторий + номер PR); её берёт и вебхук. Если ручной запрос отменил бы открытый прогон того же owner'а на **другом** SHA (например, push, обработанный вебхуком уже после чтения PR эндпойнтом), эндпойнт под блокировкой перечитывает head PR из GitHub (не дольше 10 с). Head уже не равен запрошенному SHA — тот же `409 stale_head_sha` с текущим head. Чтение не удалось или превысило таймаут — `502`. В обоих случаях ничего не отменяется, не записывается, не ставится в очередь и не публикуется. Если других открытых прогонов нет, лишнего вызова GitHub нет. Параллельные доставки для того же PR ждут блокировку не дольше этого времени.
- Если head PR сдвинулся между постановкой в очередь и стартом worker'а, worker не ревьюит новый код под старым прогоном: прогон закрывается как `HEAD_CHANGED` (статус `cancelled` на SHA этого прогона), на другой коммит статус не пишется.
- **Один коммит, два источника.** На коммите одновременно открыт не больше одного статуса. Ручной прогон с `force: true` (по умолчанию) заменяет открытый прогон на том же SHA, в том числе вебхуковый: статус старого закрывается как `cancelled`, у нового свой. Вебхук (или `force: false`) на SHA с открытым прогоном переиспользует его вместе со статусом. Worker, чей статус уже закрыл более новый прогон, больше в него не пишет. Открытый прогон, чья задача потерялась, при замене закрывается как `failure`.
- Плановые прогоны (digest) статус не публикуют: они не ревьюят head PR. Плановых задач, которые ревьюят конкретный PR, нет.
- Owner может переопределить любое из этих полей в блоке `owners.<id>.progress_status`, например `mode: off` для owner'а, у учётных данных которого нет нужного права.

## Раскрытие данных

В summary и описании только состояние, причина пропуска или код ошибки, число замечаний и ссылка на комментарий. Текста модели, деталей замечаний и текста из Jira там нет. Ключ задачи и соответствие задаче добавляются для приватных репозиториев; в публичных показывается только ключ и только при `public_repos.jira_disclosure: key_only` или `full`.

## Флаг `has_sensitive_content`

Каждый прогон ревью сохраняет `comment_url` и `has_sensitive_content`: содержал бы опубликованный комментарий ревью до применения политики публичных репозиториев детали security-замечаний или текст Jira (непройденные критерии приёмки или любой текст ревью, написанный с контекстом Jira в промпте). `NULL` — неизвестно: прогоны до миграции `008_review_run_progress` и прогоны, которые не публиковали комментарий ревью. Это задел для будущей админки; сейчас флаг ни на что не влияет.
