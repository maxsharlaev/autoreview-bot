# Roadmap: Open PR Review

План на пять месяцев после решения о публикации. Сроки ориентировочные: каждый этап завершается проверяемым результатом, а не датой. Проект развивается как самостоятельно размещаемый сервис ревью для разных команд. GitHub, Jira и Codex остаются первой реализацией, но не определяют внутренние интерфейсы будущих интеграций.

## Текущее состояние

| Область | Есть сейчас | Что ещё требуется |
| --- | --- | --- |
| Ревью | GitHub PR → ARQ → Codex CLI → JSON → комментарий | Защита от устаревшего SHA, проверка результатов, сквозные тесты |
| Задачи | Чтение Jira issue, комментарий и переход в заданный статус по P0/P1 | Правила связи с задачей, безопасные обновления, журнал решений и тесты контракта |
| Платформы кода | GitHub App или PAT | Интерфейс платформы и минимум один второй адаптер |
| Ревьюеры | Один запуск Codex CLI | Интерфейс runner, второй CLI и независимая проверка результата |
| Наблюдаемость | Метрики API/worker, алерты, Grafana, логи | Корреляция этапов, SLO, проверка алертов и раскрытия данных |
| Управление | API статуса одного запуска и снимок очереди | Опциональная защищённая админка со списком задач |
| Язык и вывод | Английский по умолчанию; `en`/`ru` для полей промпта и подписей PR-комментария; переопределяемый файл промпта | Каталог локалей, шаблоны каналов и язык на уровне репозитория |
| Качество | Unit-тесты и CI для lint, format, pytest, Docker build | Тесты с БД/Redis и внешними контрактами, локальные pre-commit хуки |

## Месяц 0 — подготовка открытого репозитория (1–2 недели)

1. Проверить лицензии зависимостей и артефактов, включая шаблоны Grafana, наряду с лицензией Apache-2.0.
2. Проверить публикуемые файлы, примеры, документацию и CI на наличие секретов и данных конкретной организации.
3. Добавить публичные `CONTRIBUTING.md`, `SECURITY.md`, правила поддержки версий и минимальный пример конфигурации без внутренних имён и доменов.
4. Сверить README с поведением кода: текущие возможности, ограничения, безопасность webhook, способ запуска, состояние интеграций. Зафиксировать базовую архитектуру и схему событий.

**Выход:** независимый пользователь может прочитать документацию и поднять сервис на тестовом репозитории; повторный аудит публикуемого Git-репозитория не находит внутренних данных.

## Месяц 1 — надёжность базового ревью

1. Перед записью и публикацией сверять `run.head_sha` с актуальным PR; отменённый или устаревший запуск не должен менять комментарий и Jira. Сделать повторный webhook и одновременные запуски атомарными.
2. Отклонять ответ модели с неверным SHA, путём вне допустимого diff, невозможной строкой или несогласованным статусом прежнего замечания. Явно отмечать неполное покрытие.
3. Сделать пустой allowlist запретом по умолчанию. Разделить авторизацию ручного API и подпись GitHub webhook; проверить права автора, работу с fork и границы sandbox.
4. Тесты: unit для переходов замечаний и верификатора; интеграционные Postgres/Redis/ARQ; сквозной прогон на синтетическом PR через поддельные GitHub/Jira API; случаи новый SHA во время ревью, повтор webhook, сбой публикации и восстановление очереди.
5. Локальные pre-commit хуки и CI: Ruff lint/format, проверка YAML/JSON/TOML, секретов, больших файлов, конфликтных маркеров и пробелов. CI должен запускать те же проверки и сквозные тесты.
6. Отделить структурированные findings и статусы от текста для публикации. Английский по умолчанию для промпта и PR-комментария уже есть; убрать оставшуюся статику в каналах и определить совместимость со старым смешанным выводом.

**Выход:** один PR и один SHA дают предсказуемое состояние; устаревший запуск не публикуется; тестовый конвейер воспроизводится локально и в CI.

## Месяц 2 — задачи и наблюдаемость

1. Вынести работу с задачами в интерфейс `IssueTracker`: поиск по ключу, чтение полей и критериев приёмки, комментарий и разрешённый переход статуса. Существующий Jira адаптер сделать первой реализацией.
2. Задать правила обновления Jira: какие результаты требуют комментария, когда допустим переход, что делать при отсутствии прав, закрытой задаче, несовпадении проекта и повторной доставке. Записывать результат каждой операции и её причину. Автоматическое создание задач оставить отдельным решением.
3. Добавить контрактные тесты Jira с обезличенными ответами API и сквозной сценарий `PR → issue → review → comment/transition`; предусмотреть режим без записи в Jira для проверки настроек.
4. Провести ревью observability: проверить имена, единицы и кардинальность метрик; связать `review_run_id` с этапами и логами; измерять время в очереди, время модели, публикацию, ошибки коннекторов и неполное покрытие. Зафиксировать SLO и проверить алерты на искусственных сбоях. Убедиться, что логи и панели не раскрывают токены, код PR и текст задач.
5. Ввести каталог переводов и версионируемые шаблоны вывода для PR, Jira, Slack и дайджеста. Настроить язык на уровне установки или репозитория, fallback на английский, предпросмотр шаблона и безопасное экранирование недоверенного текста. Проверить рендер для чистого PR, P0/P1, ошибки и неполного покрытия на каждом поддерживаемом языке.

**Выход:** состояние задачи и причины действий видны оператору; подключение Jira можно проверить без побочных эффектов; алерты показывают отказ конкретного этапа; английский вывод работает без настройки, а локализованные шаблоны проходят снимочные тесты.

## Месяц 3 — сменные платформы и CLI

1. Описать контракт `CodeHost`: событие PR/MR, получение diff и ревизий, clone/auth, права, публикация результата и повторные доставки. Перенести GitHub адаптер на этот контракт без изменения публичного поведения.
2. Добавить второй адаптер платформы после проверки спроса и доступных прав, например GitLab. Контрактные тесты должны использовать одинаковые сценарии для обоих адаптеров.
3. Описать контракт `ReviewerRunner`: версия модели, входной контекст, ограничения, отмена, таймаут, стоимость/токены и структурированный ответ. Перенести Codex CLI на контракт; подключить второй CLI с отдельным набором тестов и матрицей поддерживаемых возможностей.
4. Версионировать нормализованный формат finding и события запуска, чтобы коннекторы и CLI не зависели от схемы одного поставщика.

**Выход:** сервис запускает одинаковый сценарий ревью через два code host адаптера и два CLI runner; неподдерживаемая функция явно видна в конфигурации.

## Месяц 4 — независимая проверка и опциональная админка

1. Добавить режим кросс-валидации: основной runner формирует вердикт и доказательства; второй runner получает код, diff и вердикт и подтверждает, оспаривает или помечает каждый finding как требующий человека. Grok можно использовать как второй провайдер после проверки доступного API/CLI, условий обработки данных и стоимости.
2. Сохранять отдельные ответы, версии моделей, основания разногласий и итоговое решение. Валидатор не должен автоматически подтверждать собственный вывод; неоднозначные P0/P1 направлять человеку. Установить лимиты стоимости, времени и параллелизма.
3. Построить опциональную админку (`ADMIN_UI_ENABLED=false` по умолчанию): очередь и список запусков, фильтры по платформе/репозиторию/статусу, детали этапов, повтор безопасного запуска и журнал действий. Доступ через отдельную авторизацию и роли; ограничить вывод кода, задач и секретов. API статуса должен работать и без UI.
   Интерфейс открывается на английском и использует тот же каталог переводов для других языков.
4. Оценить качество на обезличенном наборе PR: точность P0/P1, ложные срабатывания, покрытие, согласованность двух моделей, задержку и стоимость. Включение проверки для всех запусков решать по этим измерениям.

**Выход:** оператор видит жизненный цикл задач через UI, который можно выключить; независимая проверка добавляет объяснимый результат и измеримую цену.

## Месяц 5 — публичная beta

1. Провести тест установки с чистой машины и новым проектом: GitHub и Jira, затем вторая платформа и второй runner. Опубликовать матрицу совместимости и инструкции по миграции конфигурации.
2. Проверить нагрузку, отмену и восстановление очереди, резервное копирование БД, обновление схемы, ротацию токенов и отключение интеграций.
3. Подготовить примеры деплоя с закрытыми портами БД/Redis, защищёнными метриками, TLS и минимальными правами интеграций.
4. На основании метрик качества отдельно решить, нужен ли блокирующий Check/Status. До этого результат остаётся рекомендательным.

**Выход:** публичная beta с документированными ограничениями, воспроизводимой установкой и проверенным сценарием восстановления.

## Сквозные правила для всех этапов

- Новая интеграция проходит контрактные тесты, тест отказа/повтора и проверку прав до включения в пример конфигурации.
- В тестовых фикстурах используются вымышленные организации, репозитории, задачи и токены. PR diff и задачи не попадают в открытые логи и телеметрию.
- Любое автоматическое действие в Jira или code host имеет идемпотентный ключ, аудит и переключатель включения.
- Публичная документация различает реализованное поведение, экспериментальные возможности и планы.
- Схема результата модели не зависит от языка отображения; переводы и шаблоны не меняют severity, идентификаторы, пути и машинные статусы.
